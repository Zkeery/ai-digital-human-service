# 后端第 4 阶段 · 退货探因多轮对话 · 技术开发文档

> **线路：后端（非前端 产品页）。**  
> 只覆盖本阶段。承接产品确认：问退货须先探因，确认后再引导操作。  
> **不上线、不接真 RTC。** 前端 3050 仅调用既有消息接口做验收，本阶段不改前端功能。

## 一、目标

同一会话内支持：

1. 用户：「怎么退货？」→ 先问原因／困难（已有 FAQ）  
2. 用户说明原因（如尺码不合适）→ **承接探因**，安抚并询问是否仍要退货；**仍不直接甩完整操作步骤**  
3. 用户：「确认退货」／「就要退」→ 再给操作引导  

状态落库，重启可恢复。

## 二、范围

### 做

| 项 | 说明 |
| --- | --- |
| 状态 | `dialogue_state_json.return_flow`：`idle`／`awaiting_reason`／`reason_heard` |
| 触发 | 怎么退货、退货 等 |
| 确认后再操作 | 仅「确认退货」等关键词才给操作步骤 |
| 测试 | 三轮路径；重启状态可恢复 |

### 不做

- 完整工单系统、换货履约、现网订单查询  
- 改前端大改版（除非验收文案）  

## 三、设计

### 会话字段

`sessions.dialogue_state_json`：如 `{"return_flow":"awaiting_reason"|"reason_heard"|"idle"}`

### 确定性优先

多轮由规则引擎处理；Agent 开启时把 `dialogue_state` 与上一轮意图一并传入，但仍须结构校验。规则命中多轮时，可跳过或约束 Agent，避免又讲成操作步骤。

**本阶段推荐**：退货多轮在确定性路径完成；`return_flow` 非 idle 时，先走规则再决定是否调用 Agent。

### 通过条件

1. 「怎么退货？」→ 探因口播；状态 `awaiting_reason`  
2. 接「尺码不合适」→ 承接原因；**不含**「提交退货申请」步骤清单；状态 `reason_heard`  
3. 再「确认退货」→ 操作引导  
4. pytest 覆盖上述三轮；后端重启后状态仍在  
5. README／状态／证据包更新  

## 四、验收清单

1. 3050 开始咨询 → 发「怎么退货？」→ 被问原因  
2. 回「尺码不合适」→ 被关心／询问是否仍退，不直接教点哪里  
3. 回「确认退货」→ 出现申请／寄回引导  
4. （可选）验收模式同样走通
