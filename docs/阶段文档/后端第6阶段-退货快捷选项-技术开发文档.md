# 后端第 6 阶段 · 退货快捷选项 · 技术开发文档

> **线路：后端。**  
> 承接后端第 5 阶段。不上线、不接真订单。  
> 本阶段只改消息接口契约；前端点选在 **前端第 4 阶段**。

## 一、目标（产品话）

用户走退货多轮时，不必死记「确认退货／想换货」等关键词。  
接口在回复里带上**可点选项**（`quick_replies`），前端下阶段渲染成按钮；点了等同发那句原文。

## 二、范围

### 做

| 项 | 说明 |
| --- | --- |
| 契约 | `POST .../messages` 响应增加 `quick_replies: [{label, text}]` |
| 规则 | 按当前 `return_flow`／原因类别给出选项；`idle` 时为空列表 |
| 确定性 | 选项文案由代码生成，不经模型 |
| 测试 | 问退货后有探因选项；尺码后有「想换货」等；普通问候无选项 |

### 不做

- 改口播正文逻辑（第 4～5 阶段行为保持）  
- 自动转人工、真下单  
- 本阶段不改前端页面（由前端第 4 阶段承接）

## 三、选项规则

| 状态 | 返回选项（label ≈ text） |
| --- | --- |
| `awaiting_reason` | 尺码不合适、发错货了、质量有问题、其他原因、确认退货 |
| `reason_heard` + size | 想换货、确认退货、转人工 |
| `reason_heard` + wrong_item | 要补发、确认退货、转人工 |
| `reason_heard` + quality／other | 想换货、要补发、确认退货、转人工 |
| `idle` 或其他来源 | `[]` |

点选后仍走现有 `try_return_dialogue`，不新增专用接口。

## 四、通过条件

1. 「怎么退货？」→ `quick_replies` 含探因类选项  
2. 「尺码不合适」→ 含「想换货」「确认退货」  
3. 「你好」→ `quick_replies == []`  
4. pytest 全绿；证据包更新  

## 五、验收（产品经理）

用 3050 前端第 4 阶段一起验：问退货后应出现可点按钮。  
仅验后端时：看接口 JSON 里的 `quick_replies` 即可。

## 六、完成定义

联调／手测通过后完成；未手测为「开发完成待验收」。
