## 会前 30 秒（开场固定口径）

各位好。今天材料是 **AI 数字人客服的技术接入方案**，不是上线申请。

三句先说清：

1. **基线**是现有《服务数字人》——jtalk 里用数字人播报客服答案，一期架构我们 **整体复用**。  
2. **变化**主要两块：前端可以换皮；应答链路增加一个 **可关掉的有界 Agent**。  
3. **本批只交文档**。数字人链路重、人力有限，**不承诺实现和上线**；若要 POC，需另立项、另批预算。

全量文档按飞书《项目文档》清单已齐，入口在项目 `docs/README.md`。今天主讲接入方案六块：**边界、接口、流程、部署、数据、安全**。

---

## 第一部分｜为什么还要做方案（约 1.5 分钟）

客服要降本、也要体验。数字人解决的是「感知」——有形象、能口播；真正解决率仍靠 FAQ／机器人／人工。

行业里翻车通常不是形象不够好看，而是：

- 推流失败用户干等；  
- 口播和图文不一致；  
- 模型乱承诺、乱转人工；  
- Room 打满整站不可用。

所以我们的设计原则就四条，请记住：

| 原则 | 一句话 |
| --- | --- |
| 架构不推倒 | 会话类型不新增，分流和 RTC 主链路不动 |
| 失败可回退 | 2 秒见不到推流就出图文；Agent 挂了就当没开 |
| Agent 可关 | 默认关；和分流开关互相独立 |
| 引擎外置 | TTS／CV／RTC 当外部能力，不承诺自研替换 |

## 第二部分｜系统边界：谁干什么、谁不能干什么（约 3 分钟）

请看逻辑分域：用户面对的是 jtalk 壳 + 可换肤的对话蒙层 + 数字人全屏蒙层。

背后五条链路：

1. **jtalk**：会话、消息、UI、同步计时、评价入口  
2. **会话管理／配置**：入口数字人开关、FAQ 分流标记、口播动作配置、会话「是否数字人」标记  
3. **NLP／机器人**：意图和图文答案——**继续由 jtalk 转发，数字人服务端不直连 NLP**（基线铁律，我们保持）  
4. **数字人服务端 + 引擎 + RTC**：Room、口播动作、推流  
5. **新增：AI Agent 编排（旁路）**：只产出结构化口播稿、动作意图、转人工**建议**——**不推流、不绕过分流、不写支付改资料**

职责一句话版：

- 业务对不对 → NLP／FAQ／规则  
- 好不好看、听不听得到 → 数字人引擎  
- 聪不聪明但受控 → Agent（可选）  
- 乱不乱套 → jtalk 编排与降级  

信任边界四条请安全同事听：

1. 用户内容只进受控通道，不进未授权训练接口；  
2. 密钥只在服务端；  
3. Agent 工具白名单，没有 Shell、没有任意 URL；  
4. Room 限流策略保留（基线示例：未销毁 Room 到阈值就拒接）。

## 第三部分｜接口怎么调（约 3 分钟）

说明在前：**下列是评审用契约草案，字段名对齐基线 PRD 语义；没和现网 OpenAPI 逐字段对账前，不能直接开工编码。**

### 3.1 唤醒／初始化

用户点进数字人后，jtalk 调数字人后端做 init：

- 必带：**sid**、**dProfileKey**（形象，基线四个蓝灵）、**specialTag=init**  
- 同一 sid **锁死形象**，会话中不许换脸  
- 成功：拿到／复用 room，前端进房拉流  
- 失败：按错误码弹窗——重试、回在线客服、或「人太多稍后再试」

### 3.2 每一轮应答

用户说话或打字后：

1. jtalk 后端走会话管理，拿到图文模板，以及口播／动作（来自配置，或经 Agent 生成再映射）；  
2. **并行两件事**：一边调数字人推流（content＝口播+动作）；一边把图文给前端 **hold 住**；  
3. 数字人蒙层真正开始播了，通知 jtalk 前端——再展示图文；  
4. 若 **2 秒内**没收到「开始展示」→ **直接出图文**（基线，我们不改这条底线）。

特殊指令继续用登记 ID（欢迎语 0001、转人工 0002、排队 0003、异常 0004、账单 0005 等）。**Agent 严禁自造未登记指令号**，只能映射到配置表。

### 3.3 Agent 旁路接口（方案新增）

建议形态：`compose-reply`，输入会话与用户话，输出严格 JSON：口播文本、动作意图、图文模板引用、是否建议转人工。

- 超时或校验失败 → **本轮当作没开 Agent**，走现网 NLP；  
- 转人工建议 **不等于执行转人工**——执行仍走现网业务动作。

## 第四部分｜交互主流程（约 3 分钟）——请跟我走一遍用户路径

口述路径：

「用户进 jtalk → 入口或 FAQ 命中数字人 → 看到引导浮层或卡片（同一会话只烦一次）→ 进入蒙层 → init 进房 → 欢迎语口播 → 用户问问题 →（可选 Agent）→ NLP 图文就绪 → 推流与 hold → 开始播再出字 → 多轮；能按规则打断 → 结束评价或转人工。」

三条体验铁律请产品／设计一起记：

1. **先可达再炫**：听不到也要看得见字；  
2. **身份要披露**：数字人不是真人（文案待法务）；  
3. **随时能逃**：回在线客服／转人工入口必须在。

打断优先级（基线，保持）：

- 事件消息高于 NLP；  
- 正在播事件时，NLP 不能插队；  
- 事件可以打断事件（欢迎语中点账单）；  
- 正在播 NLP 时，事件和新 NLP 都可以打断。  

Agent 默认产出算 **NLP 类**，除非显式落到已登记事件指令。

异常表不用逐条念，汇报时强调三类用户可感知结果：

| 用户看到 | 背后 |
| --- | --- |
| 重试／回客服 | Room 创建或加入失败 |
| 人多稍后再试 | 初始化限流 |
| 只有文字、没有人说话 | 2 秒同步降级或引擎异常丢弃 |

刷新、会话内 H5 返回、20 分钟内外重进：沿用基线 Room 复用／销毁策略，方案不改语义。

## 第五部分｜怎么部署、怎么灰度（约 2 分钟）

推荐形态：**不新建平行客服世界**。

- jtalk、会话、配置走现网管道；  
- 数字人引擎／RTC 继续现网或现供应商；  
- Agent 做成 **同机房可开关旁路服务**；  
- C 端换肤可以单独灰度皮肤包，但 **协议行为必须与现网一致**。

切量三层开关（务必讲清互不替代）：

1. **入口分流总开关**关 → 永远不进数字人答案分流；  
2. **FAQ／引导**控制谁被请来；  
3. **Agent 开关**默认关——即使进了数字人，也可以只用 FAQ 口播。

一键关 Agent，数字人纯播报仍应可用；一键关分流，整站回到原机器人。这是我们向运维承诺的「止血开关」设计目标（实现需另立项验证）。

容量：Room 并发、销毁延迟，**以现网配额为准**；Agent 的 QPS／超时必须小于等于用户可感知等待预算，具体数字 **待压测，本批不拍板**。

## 第六部分｜数据怎么流、合规怎么守（约 3 分钟）

主数据流口述：

「用户音文 → jtalk → 会话管理 → NLP 图文 → 可选 Agent 结构化口播 → 数字人 TTS／CV／RTC → 蒙层播放并通知前端出字 → 会话落库与评价。」

数据分类汇报口径：

| 类型 | 例子 | 态度 |
| --- | --- | --- |
| 会话元数据 | sid、是否数字人、形象 key | 跟现网客服留存（周期待确认） |
| 对话文本 | 用户话、图文、口播稿 | 会话存储，脱敏规范 |
| 媒体 | RTC 流、是否录音 | **待确认是否落盘**；默认跟现网 |
| Agent 轨迹 | 工具调用、用量 | 仅服务端；禁密钥、禁证件号明文 |
| 配置 | 分流、指令、口播动作 | 变更要可审计 |

安全合规六句（给法务／安全）：

1. 最小权限——Agent 默认只读配置＋生成结构；  
2. 高风险动作——转人工等由确定性系统执行，模型只能建议；  
3. 审计——分流变更、Agent 开关、评价可追溯；  
4. 隐私——咨询内容按客服个人信息级别保护；  
5. 出境——**默认国内**；供应商跨境必须单独立项；  
6. 内容安全——口播进推流前过现网内容安全策略（对接点待确认）。

威胁举例一句带过：提示注入诱导乱转人工 → 频控＋规则执行；错误承诺 → 结构校验＋话术白名单；Room 打满 → 限流；日志泄密 → 脱敏。

合规清单我们文档里列了勾选表（合同、留存、披露、未成年等）——**清单不是签字完成证明**，评审后请合规牵头勾。

## 第七部分｜和「全量文档包」的关系（约 1 分钟）

按《项目文档》我们交了 idea、MVP、Agent、RAG、上线后、商业化全套。汇报时观众若问「评测过了吗／调研样本多少」——标准答法：

> 标准、表结构、评测集设计已有；**真实访谈样本和模型跑分尚未执行**，评测报告是空壳，不能写成已通过。上线后分析同理。  
> 若要跑 POC，请批入口、次数、人民币上限和引擎范围，另立项。

架构选型一句话：固定工作流是骨架；Agent 是可关插件；**不上完整 Agent Harness 大重构**——这与「人力有限、架构可变可不变」一致。

请会上给方向（可「按推荐」）：

## 附录 B｜预判问答（建议背答案）

**Q：和原来服务数字人 PRD 啥关系？**  
A：主链路复用；我们补 Agent 旁路和换肤边界，并把接入六块写到可评审深度。

**Q：为什么不自己做数字人引擎？**  
A：链路重、人力有限；方案明确引擎外置。要换供应商，另立项评估合同与出境。

**Q：Agent 会不会乱转人工、乱承诺退款？**  
A：转人工只能建议，执行走规则；输出要过 schema 和指令映射；失败整轮回退 NLP。

**Q：前端换肤会不会把同步搞坏？**  
A：设计约束就是换肤不换协议；工程走查清单里有 hold／2s／进房失败用例，有实现后再勾。

**Q：Room≥30 是不是我们拍的？**  
A：来自基线 PRD 示例，**以现网配额为准**，对账后改数字。

**Q：全量文档里调研／评测是不是已经做完？**  
A：没有。是全量「方案与表结构」；样本与跑分待 POC。

**Q：今天能否批准开发？**  
A：按立项口径，今天批的是方案方向；开发要 POC／项目立项和费用闸门。

**Q：RAG 呢？**  
A：二期；一期 FAQ／口播配置；Agent 预留检索工具但不默认开。
