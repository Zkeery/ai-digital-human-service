# 后端第 7 阶段 · 退款多轮澄清 · 技术开发文档

> **线路：后端。**  
> 承接退货多轮与快捷选项。不上线、不接真支付／订单查询。  
> 前端沿用第 4 阶段快捷按钮，本阶段一般不改前端（除非契约字段兼容即可）。

## 一、目标（产品话）

用户说「退款」时，先分清情况，不要直接甩一句笼统话：

1. **已经寄回／在等退款** → 教如何看退款进度  
2. **还没办理退货** → 接入现有退货探因流程  
3. **查退款进度** → 进度话术  
4. 界面继续用 `quick_replies` 可点选项  

## 二、范围

### 做

| 项 | 说明 |
| --- | --- |
| 状态 | `dialogue_state_json` 增加 `refund_flow`：`idle`／`awaiting_clarify` |
| 触发 | 泛问「退款」（且不在退货多轮中）→ 进入澄清 |
| 分支关键词 | 已寄回／等退款；还没退货／要退货；退款进度／到账 |
| 快捷选项 | `awaiting_clarify` 时返回对应 `quick_replies` |
| 测试 | 澄清→进度；澄清→进入退货探因；问候仍无选项 |

### 不做

- 真实查单／查退款到账  
- 自动转人工、改前端视觉大改  
- RAG／多入口  

## 三、状态机

```text
idle
  └─ 泛问退款 → awaiting_clarify
        ├─ 已寄回／等退款／查进度 → 进度话术 → idle
        └─ 还没退货／要退货 → 退货探因（return awaiting_reason）→ refund idle
```

退货多轮进行中（`return_flow != idle`）时，本阶段不抢答。

## 四、通过条件

1. 「我想退款」→ 澄清口播 + 快捷选项  
2. 点／说「已经寄回等退款」→ 进度话术，无「提交退货申请」  
3. 点／说「还没办理退货」→ 进入退货探因（问原因）  
4. pytest 全绿；证据包更新  

## 五、验收（产品经理 · 3050）

1. 开始咨询 → 发「退款」→ 看到澄清按钮  
2. 点「已经寄回等退款」→ 听到查进度说明  
3. 新开一轮：「退款」→「还没办理退货」→ 被问退货原因  

## 六、完成定义

手测通过后完成。
