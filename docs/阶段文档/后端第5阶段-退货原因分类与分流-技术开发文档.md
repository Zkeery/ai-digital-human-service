# 后端第 5 阶段 · 退货原因分类与分流 · 技术开发文档

> **线路：后端（非前端 产品页）。**  
> 只覆盖本阶段。承接后端第 4 阶段「探因 → 确认 → 操作」。  
> **不上线、不接真 RTC／订单系统。** 换货／补发仅话术引导；前端 3050 只做验收入口，本阶段不改前端页面。

## 一、目标（产品话）

用户说明退货原因后，不要只用同一句套话，而是：

1. **识别常见原因类别**（尺码、发错货、质量／破损、不想要／其他）  
2. **按类别给一句针对性安抚＋可选出路**（换货／补发／仍要退／转人工）  
3. 用户说「想换货」「补发」「转人工」「确认退货」时，走对应确定性回复  
4. 原因类别写入会话状态，重启可恢复  

仍遵守：未确认退货前，**不讲提交退货申请的操作步骤**。

## 二、范围

### 做

| 项 | 说明 |
| --- | --- |
| 原因分类 | `size` / `wrong_item` / `quality` / `other`，关键词规则 |
| 分类口播 | 每类固定口播模板；要求回复关键词：「确认退货」「想换货」「要补发」「转人工」 |
| 分流关键词 | 换货／补发／转人工／确认退货 → 对应回复；转人工仅 `suggest_transfer_human=true`，不自动执行 |
| 状态扩展 | `dialogue_state_json` 增加 `return_reason_category`（可空） |
| 测试 | 分类单测＋「尺码→想换货」「质量→确认退货」「发错→要补发」路径 |
| 文档 | 本手册、证据包、项目状态、README |

### 不做

- 真实换货／补发下单、物流查询  
- 自动调用转人工接口（仍须用户点转人工）  
- 大改前端页面；3050 继续用现有输入框验收后端能力  

## 三、状态机（相对后端第 4 阶段）

```text
idle
  └─ 问退货 → awaiting_reason
        └─ 说明原因 → reason_heard（记下 category）
              ├─ 确认退货 → 操作步骤 → idle
              ├─ 想换货 → 换货话术（仍 reason_heard）
              ├─ 要补发 → 补发话术（仍 reason_heard）
              └─ 转人工 → 建议转人工口播（仍 reason_heard，suggest=true）
```

## 四、通过条件

1. 「怎么退货？」→ 探因（后端第 4 阶段行为保持）  
2. 「尺码不合适」→ 口播提到尺码／换货可能，且无「提交退货申请」  
3. 接「想换货」→ 换货引导话术，仍无退货申请步骤  
4. 「质量有问题」→ 质量类安抚；再「确认退货」→ 才有申请步骤  
5. 「转人工」在 reason_heard 下 → `suggest_transfer_human=true`，会话仍 active  
6. pytest 全绿；证据包／状态已更新  

## 五、验收清单（产品经理 · 3050）

1. 开始咨询 → 怎么退货？ → 被问原因  
2. 尺码不合适 → 听到针对性说明，可换货  
3. 想换货 → 教怎么找换货入口（话术级），不教退货申请  
4. 新开一轮：质量不好 → 确认退货 → 才出现退货操作步骤  
5. （可选）发错货 → 要补发 → 补发话术  

## 六、完成定义

手测通过后宣布完成；未手测为「开发完成待验收」。
